# 配置驱动的关卡扩展

逐关实施基线。对应[通用扩关流程](https://github.com/mxp-xc/emblem-rekindled/issues/36)，
以[迷雾森林边缘](https://github.com/mxp-xc/emblem-rekindled/issues/35)首次验证，后续沿此入口逐关核对。
本文件说明目标结构与接口；实现完成和平台验证以实施票为准。

## 选择

采用章级内容库、一份关卡定义和进入时的部署绑定。普通新增关卡填写地图、部署与事件配置；
新系统能力在通用逻辑中增加一次，再由后续关卡配置使用。主场景、战斗播放器和存档入口
不按关卡编号分派业务。原版事件仍须逐关核对，配置不会自动推断未知规则。

三个独立设计分别强调最小打开接口、可组合的固定领域操作、只补缺项的离线导入。
选取第一个的单入口，结合第二个的配置解释和第三个的资源准备方式：

- 打开关卡时集中处理来源验证、队伍槽位、静态蓝图和表现绑定，调用方取得同一份content与battle。
- 配置只表达已确认的动作和条件，如回合结束、单位显现、入场、策略变化、首领交战/死亡、战序分支和结算。
- 章级库复用人物表现与动作组合；地图只引用它们，新增内容只补缺项。

为每条路线导出完整关卡虽然容易沿用现有工具，但会重复保存地图、剧情与动作片段，
也让新增路线继续影响导入和存档。采用进入时绑定后，m2六条路线共用一份定义，
队伍人数、职业和临时部队变化都作为输入处理。首次改造集中在绑定与内容准备处，
用m0/m1回归和m2全部可达上下文控制风险。

## 内容所有权

| 内容                    | 归属与职责                                                                   |
| ----------------------- | ---------------------------------------------------------------------------- |
| 章登记、路线与招募规则  | 选择关卡配置，描述世界节点和正式成员加入顺序。                               |
| `authored/`关卡配置     | 人工核对的目标、开场、事件、对白引用与结算；生成器保留。                     |
| `generated/battles/mN/` | 原地图、规范化部署及本关来源记录；不保存某条路线的完整人物副本。             |
| `generated/library/`    | 章级角色、文本、UI、地图人物与战斗表现目录、动作组和组合片段；独立输出清单。 |
| `generated/shared/`     | 现有PNG共享所有者，继续按完整字节和导入参数复用，保留`.import`与UID。        |

公共库只按整章引用清理。重导某关不能按该关的需求裁剪公共库，也不能清理authored或其他关。
普通运行、检查和导出直接使用已提交快照；原JAR、Java绘制器和音频转换器只参与离线内容更新。

## 打开与恢复

目标interface是一次打开关卡，内部组合内容读取、配置解析和BattleState；现有命名战斗命令保留：

```gdscript
open(chapter_path, battle_id, source, random_source) -> {ok, content, battle}
# source互斥：新游戏、世界progress、战斗snapshot。
```

先校验来源与路线，再按路线前缀、招募表和真实party匹配部署槽位。party数组排列不是槽位顺序。
原版结算会恢复非必保的正式战死成员，旧槽位不重排；正常流程可从路线前缀推导招募顺序，
无需因此新增存档字段。空槽位按原部署记录顺序生成临时身份，实际部署ID与资源身份分开。

部署槽位按规范招募顺序绑定，例如0、9；原战场as遍历却保留已有formal vector顺序，
首图实际为9、0，再按原部署追加新人及其他单位。Session派生partyOrder，投影输出unitOrder，
目标遍历与最后目标经验按该顺序处理；初始化随机仍按原p记录顺序。
party数组排列、槽位顺序、初始化顺序和战场遍历顺序分别承载不同含义，不能互相替代。

新战局由一个初始化流程按原记录顺序处理装备选择、位置选择和属性成长。
原部署的0级规范为1级。
随机矩形四边包含、重叠格去重、排除占位；没有候选格时跳过该条，不无限重试或消耗临时ID。
内容读取本身不抽随机。战斗恢复根据已有campaign和实际单位建立正确蓝图，
直接校验并恢复已保存状态，不重抽位置、装备和成长。
这只约束已生成结果，不改变读档后可重新尝试未来随机结果的既有政策。
新图初始化旧成员时，原版仍先处理该部署的随机装备选择和位置选择，再绑定已有成员；
不能因成员已经存在而省掉前面的随机调用。已有物品和培养沿用成员记录；
我方原型成长为确定值计算，不额外抽成长噪声。恢复已生成战斗与进入新图分开处理。
原部署也可能以固定身份声明已在正式队伍中的成员，例如 m16 的雅木。此时按身份继承该成员，
并将其计入对应的队伍位置；没有对应旧成员的固定身份仍按新成员初始化。

失败不修改传入progress、不替换当前场景、不覆盖继续档。缺图、缺职业表现或缺动作组合
必须在开放输入和写入记录前报出关卡与配置位置；不能用另一人物图片降级。
固定部署单位必须齐全，配置中允许因空区域而省略的部署单独验证，不能简单要求所有实例永远固定人数。
保存坐标按当前地图校验，不要求单位仍在初始随机区域内；正常移动不会使记录失效。
静态名字、图片与锚点仍由当前章内容恢复，不以存档中的图片路径为权威。

原版把我方旧成员槽位和AI策略放在同一个Y字段：原部署policy32用于选择槽位，
初始化后Y保存槽位值。现代自动行动不能把该数值当作AI位标记。
因此我方部署和旧记录恢复时将policy规范为0，部署槽位单独保存；
正式成员身份、物品、培养和招募顺序沿用原值。这是明确的语义分离，旧记录验收按业务状态
及这项已定变换比较，不声称每个内部字段都逐字相同；敌方和友方的策略位继续按来源保留。

## 关卡配置

正式格式沿用JSON，不增加YAML或脚本解释依赖。字段表达以下已确认的领域内容：

- 地图、原部署顺序、角色/部署槽位、临时模板、固定格或随机区域。
- 新加入的正式成员、指挥官、胜败条件与优先级。
- 开场和目标；按实际战序生成战斗标题。
- 按单位ID或部署槽位选择目标的回合事件、入场动画与显现；策略变化不提前显现隐藏单位。
- 首领初次交战和死亡对白；一次性标记随现有事件状态保存，读档后不重播。
- 战序条件对白、路线选择或保持原路线、一次性奖励与驻留世界。

`speakers`中的`name`必须显式提供字符串；空串表示不显示姓名牌，仍保留该说话者的
阵营色调和镜头目标。未提供`portraitId`时不显示头像；提供时仍须引用章内有效头像。
缺失或非字符串的`name`不表示匿名，内容入口会拒绝该配置。

普通战斗的`combatEvents`中，`firstCombat`使用`sequence`；`unitDeath`使用
`beforeRetirement`、`afterRetirement`引用序列，至少提供一段有效序列，不支持`unitDeath.sequence`。
可见播放顺序为战斗、退场前对白、地图退场、退场后对白、奖励；缺省的对白阶段跳过。
伤害、掉落和经验仍由domain即时结算，显示阶段不重复执行结算。
首次交战尊重单位已有的原生`B & 4`标记；`map_attack`不触发普通首领交战或死亡对白，
也不消耗该首次交战标记。新关配置直接使用上述有限字段。
普通战斗的`unitDeath`可用`revealUnitIds`声明退场后逐人到达的隐藏单位。业务结算先按原顺序
处理原格及邻格占位，再检查胜败；表现层在退场动画后按同一队列播放到达，无法到达的单位保持隐藏。
事件标记与已经到达的位置随战局保存，恢复时不重复触发。

`revealUnits`仅含`kind`、`unitIds`，通过非空、无重复的ID列表指定已声明单位，只控制画面即时显现，
不移动单位、不修改属性，也不插入动画或等待。需要镜头时在它前面使用`focus`。
同一次回合事件由domain提交业务显现和一次性标记，配置序列按顺序展示各组，读档后不重播。

普通回合援军可用`arrivalMode:"nativeQueue"`选择原生逐人到达队列；完整`arrivalQueue`
按源顺序包含原地显现、邻格到达及无空邻而保持隐藏的对象。先播放共用逐人镜头与固定队列门槛，
再播放事件`sequence`；空sequence也不跳过队列。单位已由部署声明，沿现回合一次性标记恢复。

离线`deploymentAdjustments`每项以`sourceId`或`deploymentIndex`唯一选择原记录，
只允许规范化`id`或`position`；source选择有歧义时拒绝。现代实际ID与来源分开，
例如`{"deploymentIndex":25,"id":70}`保留该条source46/class24，另一条source46/class8仍用id46。
采样和发布使用同一规范化声明；原初始化暂停后才重标采样键，并显式保留source和原部署index。
画像、成长与recipe不从采样别名反推，关卡顺序及两个实际单位的独立身份保持。

有限周期克隆通过`periodicClones:{id,pool,throughRound,branches}`声明；`pool`包含两端，
`branches`每项只声明`period`和`templateUnitIds`，敌方阶段结束按数组顺序选首个整除分支，
执行至`throughRound`。模板引用来自原部署，同批先构造全部隐藏新对象，再依序显现。
无空邻时新对象保持隐藏存活并占池；回收ID后新对象追加到战场顺序末尾。
表现family继承当前模板实例的原部署来源，动态ID不新增图片或profile。
库存按当前模板物品ID、默认耐久、原G补入规则和六格容量重建，出生代分配新的持有物品身份。
`cloneState`保存`nextGeneration`及`{unitId,generation,templateDeploymentIndex}`绑定，
包含隐藏和死亡对象；持有物品的instanceId是opaque身份，代数校验不解析其字符串。
同ID更换family后刷新地图、人物资料和战斗表现绑定，保留视图及共享片段缓存。

无固定末轮的周期克隆使用互斥的`randomEachRound:{fromRound,count,templateUnitIds}`，不填写
`throughRound`或`branches`。每个到期回合按顺序带放回抽取当前模板，再逐次构造隐藏单位；
池满仍抽来源，已完成回合不重抽。出生、持物重建、到达队列和family绑定沿用同一规则。
冷恢复按已有规范事件键核对连续已完成回合和出生代数上界，不枚举未来回合；保存格式不变。

多个单位各自决定克隆时，使用互斥的`conditionalEvery:{period,groups,reservedUnitIds}`。
每个整除回合按`groups`顺序检查`whenUnitVisible`，可见时依次使用该组的`templateUnitIds`；
没有单位可用时也记录该回合已处理。`reservedUnitIds`声明池中不会由这些组直接克隆、但仍占据
静态部署身份的单位。冷恢复校验已处理回合和出生代数上界，不根据当前可见状态推断过去的触发结果。

`commanderSetup`可声明`candidateSource:"formalParty"`，与显式`candidates`、
`defaultCommanderId`互斥；按进入来源的原生`partyOrder`筛选当前可见正式成员，默认首位，
不使用招募顺序替代。`allUnitsRetired`用非空`unitIds`表达全部指定目标退场，沿单目标的
不存在、隐藏或HP耗尽语义。`focus.sourceMaxFocusPixels`只设置每次更新的最大源像素步长，
默认12，保留距离除二后的最小1像素限幅，不改变后续步骤默认值。实施与验证见
[#52](https://github.com/mxp-xc/emblem-rekindled/issues/52)。

召唤之杖59使用章级`library.summons`目录，按阵营、职业和实际来源ID显式绑定已采样profile。
同职业、阵营的多个来源ID只有在名字、头像、地图人物、战斗表现和动作完整比较一致后才共享profile；
实际ID与持有物品身份仍由战局分别分配。非敌召唤池20～29、敌池70～79，和周期克隆池独立。
召唤出生沿用通用部署的成长与属性噪声，出生后在战场遍历末尾追加；`summonState`保存出生代和
ID、职业、阵营绑定，以及出生时已完成的克隆代数。冷恢复先分离召唤单位，再校验周期克隆和
静态部署；表现从章库恢复，不信任存档中的图片路径。两种出生按克隆代数锚点和各自出生代
恢复相对遍历顺序，存档数组排列不影响顺序；结算只提取正式队伍。
该能力及现有关卡回归的实施、验证状态见[#51](https://github.com/mxp-xc/emblem-rekindled/issues/51)。

地图地点由离线导入的`map.locations`声明，保持原尾部顺序及`sourceIndex`；宝箱包含稳定`id`、
`position`、原`tileId`、`openedVariant`，以及互斥的有序`weightedChoices`或`reward`；`reward`可为固定物品或金币范围。开启图块的`map.tileVariants`
同时提供原生直接绘制的texture、terrain和各classGroup移动成本，不从地形类别猜算成本。
图块图片沿章级shared所有权发布；原图与当前战局地图分开，开启后地图和HUD读取同一投影。

`locationEvents`按`locationId`关联有序`unitIds`及可选`sequence`。领取成功后才检查组首是否
存在、存活且隐藏，再依序尝试全组到达；单人无空位不阻止后续成员。奖励领取与到达成功分别保存，
只保存实际库存、`events["location:<id>"]`及单位状态，不保存未来奖品或随机源。
加权宝箱在容量允许领取时按原权重抽一次，固定物品宝箱不抽；人物包满时自动入仓，双满不抽样、不消费地点，仍结束行动。
显式声明空结果权重的宝箱先抽取结果；空结果即使双满也会开启，抽到物品且双满时不消费。金币宝箱不受容量限制，抽取后按资金上限入账并开启。
读取配置、打开菜单和恢复记录不抽宝箱奖励。相对原版m12初载预抽四次，这改变随机调用时机；
已领取业务保持，未领取的未来随机允许重试。实现及验收状态见[#59](https://github.com/mxp-xc/emblem-rekindled/issues/59)。

m2的同一配置应表达：38条部署、7个已有成员槽位、新成员7、随机部署33/32/82，
第1/3/11轮到达、第9轮策略变化、首领82对白503/504、胜利对白505/506/507，
战序2用488否则508；没有路线选择，保持原路线并奖励1000金币。
条件仅增加真实关卡需要的明确操作，不提供任意表达式、循环、脚本回调或属性补丁。
入场偏移只影响动画起点，最终坐标仍为部署格。

## 访问与章完成合同

`map.locations`的`kind:"visit"`不声明`openedVariant`；`reward`限定为固定`item`、固定`gold`、
`weightedItem`或含两端的`goldRange`。权重以100为固定分母，剩余区间为空；
随机奖励只在确认`visit_location`时抽一次，固定物与固定金币不抽。合法尝试结束人物行动；非空物品双满失败不消费地点，
空/金币成功消费，资金按现上限钳制。消费仍记`events["location:<id>"]`，不保存未来候选、seed或失败候选。
此延迟抽样区别于原版载图预抽；宝箱的容量先检和开启投影合同保持。

`story.commanderMode`缺省为`selection`并要求一次`commanderSetup`；显式`none`禁止该步骤，
只允许从有效进度进入，普通关卡清空指挥官并保留合法`commandPolicy`；遭遇战保留已有指挥官。
`allUnitsRetired`可用于胜利或失败，
胜败按声明顺序判定。`beforeAutomaticPhase:{round,faction}`按指定自动阵营阶段应用策略变化，
与旧`beforeEnemyPhaseOfRound`互斥，不提前显现隐藏单位。
`noVisibleFaction`按指定阵营的可见状态检查胜败；仍可见但 HP 为 0 的单位在退场前仍计数。
遭遇战先检查我方全部不可见，再检查敌方全部不可见，因此双方同时退场时失败优先。
`world_encounters.gd` 保存已核对的世界敌人生成判断：进度达到 6、队伍未移动且距上次检查
至少 10000 毫秒时，按职业、已完成地点、是否出现的顺序抽样。世界地图显示对应职业的敌人；
队伍旅行经过敌人所在地点时中断并进入相应遭遇战。敌人标记随世界会话保存在内存中，
重新读取世界记录后重新生成。
`m17`、`m18`、`m19` 已登记地图与部署资源，遭遇战以 `encounter` 来源进入，未使用的部署位保持空置；
胜利时保持主线进度及遇敌位置，并恢复此前地图的队伍坐标。通关后的遭遇战保留原通关评价，
`chapterResultHistorical` 标记评价所用数据属于通关时的历史快照。
世界菜单在进度达到 6 且尚未使用时提供一次奖励关卡；确认并成功加载后，
`settings.json` 的 `bonus_battle_used` 记录已使用状态。入口在本地加载，不连接原版验证服务。
世界旅行按当前路线依次经过中间地点；旅行接口在遇敌地点中断并返回实际抵达地点。
普通访问在旅行结束后更新世界当前位置。

末节点显式声明`chapterEnd:{id,sequence}`，允许空`routeChoices`，保持当前路线。
完成进度用`chapterCompleted:true`且`worldStep==route.size()`，仍对应真实末节点和已完成战局；
它能恢复完成世界并进入遭遇战，但不能作为下一场主线战斗的来源。
普通进度仍要求`worldStep<route.size()`。
`chapterResult`保存完成时`party:[{id,level,power}]`、`gold`、`totalPower`与`chapterStats`；
人物按原ID0至9顺序展示。结果在奖励、队伍恢复后、切世界前按战术地形及实际指挥上下文计算，
不随后续世界整理重算。

`chapterStats`在战局与世界统一为`{rounds,playerRetirements,allyRetirements}`。
新局为1/0/0；缺整个字段的旧记录三项为null，已有对象必须完整且逐项合法，null沿续局保持。
回我方阶段加rounds，普通与地图伤害的无复活最终退场按阵营累计；classGroup10特殊召唤类不计，
其他召唤不能仅凭召唤身份排除。数值限制为非负安全整数，rounds至少1，上限2147483647。
评价与指挥能力由完成快照统一派生；未知历史不当作0，总战力严格大于4000仍确定SSS，其余缺历史不评级。

章末序列使用`prologue`滚动文本459；缺少原章末插图时保留深色背景，不替换为其他图片。随后三个无配置步骤`chapterParty`、`chapterSummary`、
`chapterRating`，末尾用`instruction`展示初章完和待续。主流程先保存候选再播放，失败重试同一候选；
冷读不重播，仅完成世界的“查看通关记录”只读重看三个统计步骤，不保存播放游标。
该能力只提供本地章末和完成世界，不承担第二章加载、支付或云端传档。实施及验收见
[#60](https://github.com/mxp-xc/emblem-rekindled/issues/60)。

## 表现与动作库

人物表现以独立、可读的来源recipe和职业/阵营/武器索引，不以临时ID95、地图或路线编号索引。
保留来源角色或原槽位模板，核对实际nativeSide、presentationClass、headId/headPalette、
武器帧/偏移、投射物、精灵尺寸、帧、序列与时序。仅职业相同不能证明外观相同。
不同recipe只有完整定义与图片核对一致后才允许合并；同PNG也不意味着合并角色身份或成长。

继续沿用现有actionGroup/defenseGroup及组合片段。现m0/m1有246个相同组合键，
除两项采样人物标记外JSON完全相同，可共享；实际出演者仍在运行时绑定。
新组合只在所需动作组、形状组、sourceSlot、结果或场景配置缺失时采样。
viewport、舞台、时间以及背景/天空参数不一致时，需要另行核对，不能仅凭人物几何复用。

库先覆盖已有功能与本轮可达人物、职业和合法装备。新增能力需要的缺项明确补导，
不提前生成所有未实现晋升组合。复用由显式目录、来源和生成参数决定，不新增摘要缓存；
生成规则改变时显式刷新，既有引用和人工素材受所有权保护。

## 晋升与培养边界

章 `rules.promotions` 从原职业表导出当前六族的 `fromClassId`、`toClassId`、
`minimumLevel` 和八项 `gains`，领域、绑定和持久化共用这份数值。
`UnitProgression` 集中资格、固定变换与数值上界；手动76和普通升级恰好到门槛后的自动76
调用同一变换。等级、经验、熟练与当前HP保持，固定增量可超过普通成长上限。
普通成长仍按原上限抑制新增量，保留已有超限值；果实按其固定上限处理。

正式成员的原职业由可信stage0来源profile推导，蓝临时成员由原部署声明推导。
投影的 `promotionBaseClassId` 是静态蓝图信息，不从存档读取；只有匹配的合法stage1
才允许普通上限加该族固定增量。原本已stage1的临时部队和普通敌人不因此获得额外上界。
临时成员冷读仅接受原stage0到同族stage1，仍保留原source、槽位和deploymentIndex。

晋升表现继续按source/slot、class、faction recipe登记。离线准备真实执行原76，
只合并表现库，不改原部署；准备模式与来源写入provenance，可由正式工具重建。
关卡需显式登记自身可达的晋升变体，章库存在某profile不自动开放所有关卡。
例如m0没有76的正常取得路径，不登记晋升变体；不得为受控注入76而自动采用全库兜底。

Content为当前stage0蓝单位预检目标profile、地图与动作，派生 `promotionTargets` 和
`promotionErrors`。未来表现缺项不阻止无关的旧图加载；持有76的相关提交必须在改职业、
扣物品或抽业务随机前通过预检，共享经验和杖经验的自动晋升同样适用。
晋升成功后沿现reproject/rebind更新地图、资料与独立战斗，保存只记录已经提交的战局。
