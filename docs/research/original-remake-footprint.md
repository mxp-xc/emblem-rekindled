# 初章原版与重制版：资源和数据组织对照

调研日期：2026-11-04。范围是本地初章 JAR、当前工作区的初章内容和相关生成、读取代码；迁移前统计使用 Git 跟踪路径，迁移后数量按工作区初章目录实际文件计数。未比较第二章、终章，未运行实际平台性能测试，也未逐项反编译原版算法。数字不能直接代表最终包体积或运行内存。

## 结论与优先顺序

1. 人物表现库重复数据已按完整定义共享：611 个 profile 内有 3,898 条武器外观引用，对应 932 种定义；611 条地图动画引用对应 56 种定义。保留角色身份、职业、阵营和合法装备约束；离线往返和定向场景已检查，实际平台包和手机内存收益仍需验证。
2. 地图绘制和移动代价均在导入时展开：20 张地图有完整 PNG 和逐职业逐格代价。可先比较“格子图 + 图块运行时绘制”“图块/职业代价表 + 特殊格子”两个小试验；验证更新地图、宝箱、阻挡与性能。减少 PNG 字节未必减少文件数量。
3. 人物部件运行时组合的受控样本已逐帧对照；仍需覆盖更多角色上下文，确认图片替换、投射物与平台行为，才能估算全章收益。
4. 音乐 MIDI 展开为 Ogg 是可见的体积差异，但当前免运行时合成器；除非交付体积确实是问题，否则不应只凭原版文件小就增加跨平台合成器。

## 原版资源包与运行时组合

本地初章 JAR 307,882 bytes，内含 `1.pak`，压缩后 127,328 bytes、展开 189,008 bytes。按 [现有读取代码](../../tools/emblem_dev/content/definitions.py) 的目录格式只读解析：包有 402 个命名条目，含 331 个 PNG、31 个 `.sp`、7 个 MIDI、32 个无扩展名条目和 1 个 `.prop`；索引与数据长度之和恰好覆盖包。原版反汇编观察到按名称读取 `.sp`；本次未完整解析 `.sp`、逐项核对素材的运行时使用或画面组成。

当前离线导出器在不同人物和武器组合下调用原版绘图器，[逐帧输出图片和偏移](../../tools/resources/content/Chapter1BattleAssets.java)；地图人物也[绘制每个活动帧及行动后状态](../../tools/resources/content/Chapter1MapAssets.java)。图集迁移前初章有 1,136 张 PNG 和 1,142 个 `.import`（包括六条 Ogg 的导入描述）；其中 1,135 张位于 shared。迁移后这 1,135 张分别作为逻辑区域存于 13 张 PNG 图集，应用图标单独保留；初章目录共 151 个文件（包含 JSON、图片、音频和 `.import`），低于原 `1.pak` 的 402 个命名条目。扩大到整个 `game/`、包含测试素材和非代码文件，排除脚本、脚本 UID、工程配置及 `.godot` 缓存后共 311 个；这两个上限均有自动检查。这是文件数量对照；图集中仍有多个预合成帧，不能说已按原版部件组合。

图集按 PNG 解码后的尺寸和完整 RGBA 保存，原图的导入参数和 UID 记录在来源清单；重新导入时在隔离副本还原散图，完成所有权和共享检查后再打包。清洁 Godot 工程中逐张核对 1,135 个逻辑区域的解码 RGBA 与迁移前图片一致，实际 m17 采样连续两次重导入无文件变更；另在隔离副本修改该采样的一帧，确认新图片可发布并从图集完整还原，第二次重导入没有文件变化。单张原图可由 `er extract-texture` 导出，人工替换仍使用逻辑路径。图集导入关闭透明边缘修补以保留每个区域的 RGBA；游戏使用最近邻过滤。Web 标题画面及 Android 首关真实输入已检查；设备性能和所有场景的实际画面尚未全面测量。

本次 13 张图集的 PNG 文件合计 3,672,441 bytes、像素面积 9,772,080；迁移前全部 1,136 张 PNG 合计 2,790,801 bytes、像素面积 9,238,015。图集的源文件字节更多，分配面积约增加 5.8%；这些源文件统计不能直接当作最终 PCK/APK 或显存测量。图集主要满足文件数量目标，实际包体、加载及设备内存仍需测量。

**可行方向**：离线提取基础图片和清晰定义，在 Godot 运行时组合身体、武器、头部等；先验证素材引用、帧、偏移、画面层次、朝向、颜色与透明边缘。正式运行继续使用转换后的资源，不依赖原 JAR 或原版字节码解释器，符合[工程组织基线](../design/project-organization.md)。

**代价及验证**：尚不能证明现有导出字段足以重建全部部件和规则；需查清缺项、处理动作/阵营/晋升/投射物及独立替换图片的契约。建议一个普通人物、两种武器和两侧姿态，逐帧对照现有渲染结果、真实演出和设备表现后再估算。图集保留预合成帧、减少文件数，与运行时部件组合是两个不同选择；归档只减少仓库条目、展开后文件仍存在。

可复现的首个样本：章库 `source_10_job_8_faction_1` 为左侧、`source_65_job_8_faction_2` 为右侧，均登记武器 21、22，各武器外观均有 7 帧；两者均为 `classId=8`，但身份、阵营和配色仍须分别对待。先用明确的原版采样上下文导出这四组的基础图、层次、帧引用、绘制方向、调色和偏移到隔离目录；对每帧在一致画布和锚点下调用候选组合绘制，再与当前对应 PNG 加其 `offsetX/Y` 的图像逐像素比较，记录透明边缘及尺寸差异。随后核对真实动作序列与独立战斗的时序、遮挡和投射物；此样本不代表全部职业或特效。人工换图分别验证替换单个部件和所有引用方的生效范围。成功标准还包括从保留的转换后素材在无原 JAR 的隔离 checkout 导入/构建、Android/Web 真实包可见结果与原版及当前实现一致。只在准备来源时读取原 JAR；不得以空缺贴图回退掩盖失败。

已在系统临时目录完成上述四组受控样本的静态图层试验：原版初始化后分别抽取身体、头部、武器及帧引用和坐标，Java2D 与原版绘制的 28 帧在 256×256 同一画布上逐像素 RGBA 差异均为 0；Godot 4.7.2 的 Compatibility 渲染器在透明 SubViewport 中逐帧绘制并对照，同样 28/28 帧差异为 0。四组样本的 28 个帧引用对应 22 张不同的现有完整帧；拆出后得到 20 张不同图层，样本只减少 2 张图片，不能按 28 到 20 推断实际节省。试验未覆盖其他职业、`i=true` 的源图区域裁切、程序绘制、完整动作时序、人工替换及 Android/Web；层顺序、帧长度和原始调色必须按已初始化对象处理。临时样本包含原版素材，不放入共享仓库。

进一步按初章 m0 初始部署与章库的同来源、职业、阵营及武器交集采样：27 个原始单位、9 个职业、3 阵营共 138 组外观、896 帧，在 Java2D 下与原版逐像素比较全部一致；按像素去重为 109 张完整帧，分层后为 69 张基础图。未出现源区裁切、程序绘制或抽样失败。此样本覆盖面仍限于 m0，Godot 逐像素结果仍仅有上述 28 帧；69 张基础图不包含独立投射物、地图、特效和 UI，不能推断整个仓库的减少比例。

再按已有采样记录准备 55 个关卡、路线、晋升、召唤和自动选阶上下文，分别以原版绘制结果与 Java2D 组合结果比较；重叠计数的 18,007 组、107,610 帧均一致。在此基础上，再把结果与当前 catalog 对应图片的 RGBA、裁剪尺寸和偏移逐项比较：611 个 profile 中有 536 个的全部武器匹配，3,898 条绑定中有 3,586 条匹配；其余 312 条尚未找到一致结果，其中 47 条有候选但像素或边界不同，265 条没有遇到候选。角色、职业、阵营和武器不足以唯一确定 slot 外观，必须保留实际队伍和关卡上下文。抽样探针只在内存验证，除最初四组以外尚未生成可供游戏使用的图层资源；Godot 全量绘制、替换图片契约、飞行物和实际动作时序均未覆盖。采样使用本机原版与模拟器，历史记录用于选择上下文，不能作为本次模拟器身份验证。

## 人物表现库：重复的外观定义

转换前[章库](../../game/content/chapter_1/generated/library/catalog.json) 有 611 个 profile。对每个 profile 的 `appearances` 下每一项使用完整 JSON 值比较（键顺序归一，包含图片路径等字段）：3,898 项中 932 个值不同、2,966 项是重复值；全部条目紧凑 JSON 合计 7,784,266 bytes，不重复的值合计 1,865,745 bytes。这说明**原描述值重复**，不说明人物或武器身份可合并，也不等于可按差值直接节省运行内存。

现有[章内容设计](../design/chapter-content.md#表现与动作库)明确人物来源、职业、阵营、合法装备和外观判定，不能仅按职业合并。现在章库用 `appearancePool` 保存完整外观、profile 显式引用；关卡投影按当前单位复制所需的外观，保持角色与武器身份。一次性整理后将整个章库展开，与转换前逐值比较一致；原生 m17 样本的重导入 dry-run 与原格式结果一致，隔离副本连续两次实际导入的文件字节不变。投影、贴图替换、晋升、召唤与工具测试的具体范围仍以实施结果为准。

2026-11-04 本机做了纯数据隔离试验：按完整 JSON 值分组，将 3,898 条外观值替换为 932 条共享值的整数引用，再逐项深复制还原；还原后整个 catalog 与原数据相等。当前紧凑 JSON 为 9,541,079 bytes、gzip 为 285,961 bytes；试验格式分别为 3,634,263 bytes、135,850 bytes。Python 3.14 连续 7 次解析的中位数分别为 70.92 ms、24.97 ms；`tracemalloc` 解析峰值分别为 44,998,304、17,584,381 bytes。这只测量 Python 进程中两种 JSON 格式，不含引用展开和 Godot 解析、投影、导入或最终 APK，不能作为运行时收益。实验按排序后的完整 JSON 值比较，不计算摘要；不同身份保留各自 profile。可复现方法：读取 catalog，遍历每个 profile 的每条 weapon appearance，以 `json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 为键建立顺序池，用池索引替换，再深复制引用还原并比较整个 JSON；均用紧凑序列化及 `gzip.compress(..., mtime=0)` 测量。一次性脚本和隔离测量入口保留在本机 `temp/code/`，不参与正式运行。

进一步在复制的 Godot 4.7.2 headless 工程中，临时让章投影按整数索引读取共享外观，其他资源保持原样；分别读取原版库与试验库、打开 m0 各 5 次。原库直接 JSON 读取分别为 210～231 ms，试验库为 76～83 ms；`load_chapter` 分别为 268～291 ms、138～142 ms。对 m0 的单位、部署、地图动画、战斗表现、界面等选定投影字段做 JSON 值比较，结果相同。这只覆盖默认 m0、空图片替换表和本机未压缩 JSON，未测 Android/Web、gzip、峰值内存、其他关卡、晋升、召唤、错误输入或导入重入；它证明可以继续做真实格式变更，不证明已满足交付条件。

实际采用稳定字符串引用后，格式化的源 catalog 为 5,873,047 bytes，紧凑序列化 3,716,211 bytes，gzip 为 139,605 bytes；与上述整数索引试验略有差异。新增一项外观的隔离实验中，已有 3,898 个武器引用均未变。以上 gzip 是按正式构建算法计算，不代替对实际导出包的验证。

采用实际字符串引用的代码和快照后，另一次相同设备的隔离 headless 测量中，5 次未压缩 catalog 读取为 82～91 ms，m0 `load_chapter` 为 147～156 ms；该批次与原库试验不同时运行，不能当作严格的配对平台性能实验。实际 Android/Web 包仍须核对。

随后将 611 条地图动画按完整定义共享为 56 条，保留每个 profile 的独立引用，关卡投影时深复制。一次性迁移将新库展开后与迁移前完整库比较一致；定向检查覆盖地图行动完成状态、图片替换、克隆、召唤和 m5/m6 内容。此步前后按相同方式紧凑序列化，catalog 从 3,716,211 bytes 降至 3,246,203 bytes，gzip 从 139,605 bytes 降至 131,166 bytes；尚未对新增步骤单独测量加载或设备内存。

转换前源 catalog 16,710,223 bytes；按构建逻辑紧凑序列化为 9,541,079 bytes，gzip 后 285,961 bytes。正式 [er 构建](../../tools/emblem_dev/commands/build.py) 已做紧凑和 gzip，导出包使用压缩版，[运行时完整解压并解析](../../game/app/json_document.gd)。所以不能把 16.7 MB 直接当成正式包大小或运行时内存；实际游戏卡顿和手机内存变化尚未测量。`provenance.json` 保存 24,264 条来源映射，按 [导出配置](../../game/export_presets.cfg) 排除来源记录；它主要影响仓库和导入维护，不能算到发布运行包。

这些来源映射指向 967 条不同目标路径。现在按“目标路径 → 来源列表”分组，格式化后的来源清单从 4,333,461 bytes 降至 2,258,168 bytes；展开后与迁移前全部映射一致。来源名称是导入时的相对路径，图集化后不要求作为散图存在。核对了全部 24,291 条章内来源映射，目标均能解析，且仍被章内配置引用；其中 21,544 条战斗帧来源与现有 profile、武器、帧及目标逐一一致。真实 m17 样本的无变更重导入及改变一帧后的发布、再次导入在隔离副本中通过；目标分组主要减少工作区文件体积，不改变运行包。

## 地图：预绘制整图及逐格移动代价

原 `1.pak` 中 `m0`～`m19` 共 12,092 bytes，包含地图数据和部分位置数据；`m0` 为 560 bytes。当前生成器读取原版网格，把每格的图块绘制成完整地图图片，同时保存图块、地形和移动代价（[ImportChapter1.java](../../tools/resources/content/ImportChapter1.java)）。迁移前 20 张地图 PNG 共 1,805,519 bytes，`m0` 地图 PNG 为 123,956 bytes；这些画面现为图集区域。另有 20 份 `map.json` 共 559,236 bytes。原数据与重制结果包含内容和用途不同，不能把体积差直接解释为浪费。

生成器对每个关卡的每个格子及 0～10 职业组调用原版移动代价方法并保存二维表；[MapRules](../../game/gameplay/map_rules.gd) 查逐格结果，战局可在宝箱等地形变化时更新它们。20 个文件紧凑 JSON 合计 352,817 bytes，其中 `movementCosts` 的值合计 283,283 bytes。数据在可读、确定及无需运行原版规则上有价值，但对每个格子存一遍同一结果可探索收拢。

实测静态 20 张地图：同一地图、相同职业组与 `terrain` 仍出现 6 组不同代价。例如 m8 中职业组 8、terrain 10 通常代价 1，但图块 70/71 的部分格子为 1000；所以**不能直接以职业组和 terrain 二维表替换**。本次样本中，以职业组和 `tileId` 组合检查，地图内及跨地图均未发现不同代价；这只是已导出静态格子的观察，不能证明所有动态状态、未来章和其他原版上下文都成立。候选方案须先核对原版实际条件和宝箱开启等动态变更，再决定是否采用小表与显式例外，并与所有原始样本逐格比较。

本地原版 `b.class` 的 `a(int,int,byte,byte)` 字节码进一步说明了该差异：方法先检查地图边界，再查询占位及阵营；职业组 8 对地形 5/6 返回代价 2，在其他地形上图块 70/71 返回阻挡代价 1000，其余情况返回 1。重制版导入时暂时清空单位、逐格逐组调用原方法保存静态代价；运行时 [MapRules](../../game/gameplay/map_rules.gd) 再处理敌军占位。原版边界返回值与重制版先做边界判断的表示不同，应以实际可达结果比较，不能只比较数值。

本机按 `(classGroup, tileId)` 遍历 20 张地图全部 117,162 个移动代价值，得到 979 个不同组合、0 个静态值冲突，并以该表逐格还原全部原数组。当前 `movementCosts` 的紧凑值共 283,283 bytes，试验表按字符串键序列化为 14,292 bytes；它没有计入新格式的解析代码、动态例外、导出压缩或新章。七张地图还声明开启宝箱后的独立图块和全部职业组代价：77 个声明合计对应 11 个静态表中尚不存在的 `(classGroup, 88)` 键，代价值均为 1。此统计没有执行动态事件或原版分支，不能据此发布新格式。

补充对比：将每张地图的逐格代价临时替换为该图的职业组/图块表，20 份紧凑 JSON 从 352,817 bytes 减至 127,651 bytes；各文件分别 gzip 后合计从 26,428 bytes 减至 20,809 bytes。这不是 APK/PCK 或内存实测，但说明压缩后节省量可能很小。若真正替换还需修改生成器、内容校验、战局恢复、已开启宝箱及多份 fixture；本阶段暂不为这一文本节省引入格式变更，后续以实际加载/内存瓶颈和动态地块证据重新评估。

原实现中，[MapRules.field](../../game/gameplay/map_rules.gd) 每扩展一个候选格就调用 `unit_at` 线性扫描单位，AI 也调用 `field`。每次计算临时建立坐标索引可以减少重复扫描；由于不跨调用缓存，移动、显隐、退场和援军变化会在下一次计算中反映。原版同类实现尚未对照。

隔离 Godot 4.7.2 headless 基准使用 m0 地图和 32 个固定部署坐标，其他属性受控设为同一职业组、移动 6、存活可见、两方阵营；同一输入重复 100 次，原实现约 160.1 ms、单次构建占位索引的候选约 17.4 ms，56 个可达格结果相等。另一个 40×40 合成地图分别放 20/100/300 个单位，100 次原实现约 244/1021/2978 ms，候选约 36/37/43 ms；输出相等。这是本机受控微基准，存在坐标重叠，保留原有先遇到的有效单位语义；不能推断真实整回合耗时、手机性能或原版速度。实现采用每次 `field` 重建索引，不跨行动缓存；已有移动、AI、宝箱行动定向测试通过。

完整地图图片由 [tactical_map.gd](../../game/features/tactical_map/tactical_map.gd) 直接加载和绘制；运行时逐格画图可复用图块，可能降低地图图片字节，但需要核对动态地块、裁剪、像素对齐及绘制成本。图块共享、图集、整图各有取舍，文件数和性能不能预先承诺。

## 音频：事件序列转换为录制音频

原版六条对应的 MIDI 合计 24,494 bytes；重制版六条 Ogg 合计 3,493,686 bytes。重制版把 MIDI 离线合成为音频，使用 JDK 默认音色，音乐循环和平台播放约定见[开发说明](../development.md#原版资源整理)。两者编码和音色实现不同，体积对照反映格式选择，不是同一表示的压缩率测试。

保留 MIDI 并在运行时合成可能减小音乐文件，但需随包提供合成器和音色，处理 Android/Web 兼容、解锁、循环时序、内存、CPU 和音色；最终包体与听感都需实测。更低码率 Ogg、共享音源或运行时 MIDI 都只是候选，当前没有音质和完整包对照数据。

本机用 `ffprobe` 核对六条 Ogg 均为双声道，时长约 4.2～63.8 秒。各曲解码前 10 秒后，左右声道差值 RMS 与平均信号 RMS 的比值约 0.27～1.03；这是左右信号不同的证据，不是听感或质量评价。不能假定它们为双声道重复的单声道而直接合并；有损重编码、降采样、单声道或 MIDI 合成均需先做循环边界和听感比较。本阶段保留现有音频。

## 战斗算法、事件与运行时复制

当前章库 `stage_0` 有 121 个 actionGroup、31 个 defenseGroup，`clips` 为空；[战斗演出准备](../../game/app/battle_clip_library.gd) 按实际攻击者、结果和投射物判断是否在运行时生成，不应按历史调研中采样片段的数量判断当前空间成本。现有战斗演出推进、血量、人物运动和部分效果已经在运行时计算；人物外观帧则仍从预合成图片读取。不能把整个演出描述成逐帧录制。旧片段路径仍有代码分支，但仅凭当前章库为空，不能判断其他输入或未来章是否需要，也不能直接删除。

战斗规则、AI 和移动成本在原版及重制版的具体算法复杂度没有完成逐函数对照。本次看到 [TacticalAI.plan](../../game/gameplay/tactical_ai.gd) 对每个可用装备、地图格子及目标进行评分，并调用移动范围计算；[MapRules.field](../../game/gameplay/map_rules.gd) 在扩展候选格时线性查找占位单位，[BattleState.preview_move](../../game/gameplay/battle_state.gd) 又会重新计算移动范围。可以测量密集单位、较大地图与自动阶段的计算次数和耗时，再比较复用局部占位索引或范围结果的收益。缓存必须覆盖移动、地形改变、阵营、显隐、援军、召唤、退场等失效条件，并保持相同评分、遍历顺序和同分决策；当前没有性能证据，也未证明原版算法更快。

[章加载](../../game/app/chapter_content.gd) 读取完整章库，重投影时复用已读的库；[章投影](../../game/app/chapter_projection.gd) 对外观、动作等构造深拷贝。[战局](../../game/gameplay/battle_state.gd)、战斗结算和存档流程也在多处复制状态。可针对开关卡、晋升和召唤场景分别记录解析、投影次数、耗时与峰值内存，检查可证明不可变的数据是否重复复制；不能仅按 `duplicate(true)` 出现次数认定浪费，复制也承担隔离已保存状态、回滚和防止共享对象串改的作用。原版相应生命周期和内存使用尚未做对照。

## 存档、测试与工具的不同职责

原版 JAR 包含 Java 运行代码和游戏资源；重制仓库另外包含运行时外的测试、内容提取、构建和平台验证。当前 [BattleStore](../../game/persistence/battle_store.gd) 使用结构化 JSON、校验和临时文件替换，服务于战局恢复与错误报告。它与原手机的存档机制尚未作逐字段比较；体积和代码数量更大不能直接证明存档设计冗余。对存档的简化须保留正式队伍与临时部队身份、持有物品状态、跨关进度和失败后保留原记录等契约。

静态字节码显示，原版通过 J2ME `RecordStore` 保存紧凑的 byte/int 数据；本次尚未完整还原其存档字段。重制版打开存档列表时逐槽解码和验证，存在同次操作重复读取、投影章内容的路径，实际耗时和热缓存收益尚未测量。后续若要共享读取结果，仍须独立验证每个槽，并处理损坏槽、跨关和文件变化。另有一项已经明确的原版行为差异：原版 m12 初次载图预抽宝箱，而重制版在允许领取时抽取，未领取的未来结果允许重试；具体约定见[章内容设计](../design/chapter-content.md#关卡配置)，不应称为完全一致。

本次调查时 Git 跟踪的 `game/tests/` 下有 314 个 GDScript 测试文件，合计 1,625,488 bytes；[导出配置](../../game/export_presets.cfg) 排除测试。测试代码不是玩家运行包的膨胀来源。此前 24 个测试文件从 m4 测试借用受控回合推进，现已移至 [phase_driver.gd](../../game/tests/support/phase_driver.gd)，m4 自身也复用同一入口；25 个直接使用方定向测试通过。m7 原速入场测试曾在 10 秒上限超时，延长诊断中第 5 回合实际演出耗时 7.22～9.72 秒，且超时时队列仍在推进；测试将上限改为 20 秒，保留原速和全部行为断言，修改后通过。m9 的受控边界准备现由 [m9_scenario.gd](../../game/tests/support/m9_scenario.gd) 提供，m9 和 m15 流程共享；六个相关流程测试通过。章末测试仍复用章会话测试，应分别判断其共享的业务准备，不机械移动所有测试。原版 JAR 没有随包测试不能证明这些测试不需要。

本地已有 Android APK 压缩后约 40.2 MiB；其中 `libgodot_android.so` 的 ZIP 压缩数据约 24.3 MiB，六条导入 Ogg 合计约 3.3 MiB。该 APK 是已有本地产物，未核对其 buildId 与当前源码，因此这里只表示该文件的构成，不代表本次源码的交付结果。引擎、字体和跨平台运行能力与原 J2ME 环境不同；优化资源前应先明确目标是仓库条目、开发体验、启动/内存、下载包还是设备性能。

传送、治疗和退场时间线分别由对应播放逻辑消费，模型只保存确定性的 tick、门控和画面位置；现有测试可直接检查治疗血量递增、退场对话门和效果帧边界。把它们并入播放器可减少三个源码文件，但会让这些时序断言依赖场景、计时器和绘制节点，当前没有证明能降低整体维护成本，因此保留。阶段推进在 [main.gd](../../game/app/main.gd) 中协调战局提交、入场绑定、动画和失败提示；多个关卡流程测试直接调用 `_present_phase_events`。这是一处实际跨层耦合，但该方法还负责已提交批次中后续入场的隐藏、撤退时旧画面的保留以及失败处理；简单移动函数不能消除这些依赖。若继续重构，应先通过公开的阶段推进入口覆盖这些顺序和失败行为，再确定协调器边界；现有局部证据不足以证明直接拆文件会改善设计。

## 对比边界

原版 JAR 只包含可执行与运行资源；重制仓库还包含 Godot 工程、调试工具、测试和平台能力，不能只比较总文件数或源码长度来判断设计优劣。当前测试、存档、触控、适配、导入校验等承担的跨平台与开发需求不应简单按原手机实现删除。本记录区分已实施改动、隔离试验与尚待验证的假设；定向测试和本机微基准不能代替完整平台验证。
